# Product Requirements Document

## Training Analytics, Search, Calendar & Goals

### 1. Objective

Expand the training management experience from basic workout storage and visualization into a practical system for understanding current training status and planning future training.

The iteration must introduce four connected capabilities:

1. Training-load and trend analytics.
2. Search and filtering for the Trainings list.
3. A week/agenda-first training calendar.
4. Goals and weekly training schedules.

The implementation should remain simple and appropriate for the current single-user, work-in-progress application. It should not attempt to establish a final long-term data architecture.

---

## 2. Scope

### In scope

* Dashboard analytics covering the user's current training state.
* Weekly and monthly training-volume trends.
* Pace and heart-rate trends over time.
* Personal bests by distance.
* Training list search and filtering.
* Week/agenda calendar as the primary calendar view.
* Navigation between weeks.
* Definition and display of training goals.
* Weekly distance goals.
* Definition of planned training sessions.
* Ability to predefine a weekly training schedule.
* Comparison of planned versus completed training where data is available.

### Out of scope

* Multi-user functionality.
* Social features.
* Coaching or automatic training-plan generation.
* Advanced physiological modeling.
* Complex predictive analytics.
* Race-performance prediction.
* A finalized long-term database/file-storage architecture.
* Automatic modification of an existing workout based on analytics.
* Complex recurring-calendar functionality beyond what is required to define a weekly schedule.

---

# 3. Training-load & Trend Analytics

## 3.1 Objective

Provide a complete dashboard showing the user's current training state, recent workload, longer-term trends, and notable performance achievements.

The dashboard must make it possible to answer:

* How much have I trained recently?
* Is my training volume increasing, decreasing, or stable?
* How are my pace and heart rate evolving?
* What are my best performances at common distances?
* How much of my planned training have I completed?

## 3.2 Dashboard

The dashboard must provide a concise overview of the current training state.

It should include:

* Current week distance.
* Current month distance.
* Number of completed sessions.
* Recent training volume.
* Weekly training-volume trend.
* Monthly training-volume trend.
* Pace trend.
* Heart-rate trend.
* Personal bests.
* Progress against active goals.

The dashboard must allow the user to distinguish between completed training and planned training.

## 3.3 Weekly mileage trends

The system must calculate and display training distance aggregated by calendar week.

The visualization must:

* Show multiple consecutive weeks.
* Make increases and decreases in volume easy to identify.
* Use completed training only.
* Allow the user to understand the current week's position relative to recent weeks.
* Handle weeks with no training without breaking the trend.

The exact number of historical weeks may be chosen based on available data, but the visualization must contain enough history to identify meaningful trends.

## 3.4 Monthly mileage trends

The system must provide an equivalent monthly distance trend.

It must:

* Aggregate completed training by calendar month.
* Display consecutive months.
* Include months with zero activity.
* Clearly identify the current month.
* Allow comparison between recent months.

## 3.5 Pace trends

The system must display pace evolution over time for compatible training data.

The system must:

* Use recorded training data containing sufficient distance/time information.
* Avoid combining fundamentally incompatible activity types in a misleading way.
* Present pace as a time-per-distance metric.
* Aggregate or summarize data consistently across the selected period.
* Make the direction of change understandable.

Where data quality does not support a reliable pace value, the system must omit that data point rather than displaying a misleading value.

## 3.6 Heart-rate trends

The system must display heart-rate evolution over time when heart-rate data is available.

The visualization should support identifying changes in:

* Average heart rate.
* Training volume associated with that heart rate.
* Heart-rate behavior over time.

Missing heart-rate data must not prevent other analytics from being displayed.

## 3.7 Personal bests

The system must identify personal best performances for relevant distances.

At minimum, it must support common running distances such as:

* 1 km
* 5 km
* 10 km
* Half marathon
* Marathon

The system must only identify a personal best when the available recorded data supports a valid performance for that distance.

Each personal best should display:

* Distance.
* Best time.
* Date achieved.
* Relevant training/session reference where available.

The design must avoid presenting an approximation as an exact personal best.

# 4. Training Search & Filtering

## 4.1 Objective

Make the Trainings list usable when the number of stored workouts grows.

## 4.2 Search

The Trainings page must provide a search mechanism.

Search should be able to find relevant trainings based on available textual metadata, including training names and tags.

Search results must update without requiring the user to manually navigate to another page.

## 4.3 Filters

The user must be able to filter trainings by:

* Tag.
* Date range.
* Distance.

The filters must be combinable.

For example, the user must be able to request:

> Trainings tagged "intervals" between January 1 and January 31 with distance between 5 km and 15 km.

## 4.4 Filter behavior

The interface must:

* Clearly show which filters are active.
* Allow individual filters to be removed.
* Provide a simple way to clear all filters.
* Display the number of matching trainings where practical.
* Preserve the existing training-list functionality.
* Handle zero-result searches clearly.

Filtering must operate on the training data already available to the application.

---

# 5. Calendar & Agenda

## 5.1 Objective

Provide a planning-oriented calendar where the week is the primary view.

The calendar should allow the user to understand both what was completed and what is planned for the current week.

## 5.2 Main view

The default calendar view must be a weekly agenda.

The week must be the primary unit of navigation and interaction.

The view must display:

* Monday through Sunday.
* Planned training sessions.
* Completed trainings.
* Training status for each day.
* Basic training information such as distance, type, or title where available.

The current day must be visually identifiable.

## 5.3 Week navigation

The user must be able to:

* Move to the previous week.
* Move to the next week.
* Return to the current week.
* Identify the displayed week/date range.

Changing weeks must not require a full page reload.

## 5.4 Planned versus completed sessions

The calendar must visually distinguish:

* Planned sessions that have not yet been completed.
* Completed sessions.
* Planned sessions that correspond to completed training.

The distinction must be understandable without relying exclusively on color.

## 5.5 Day interaction

Selecting a training or planned session must provide access to its relevant details.

The user must be able to understand the difference between an actual recorded training and a planned session.

## 5.6 Calendar data consistency

A training recorded in the Trainings section must appear on the appropriate calendar date.

A planned session created in the calendar/schedule must appear in the appropriate week and contribute to planning-related dashboard information.

# 6. Goals & Targets

## 6.1 Objective

Allow the user to define measurable training objectives and use them as a reference for current training progress.

## 6.2 Goal types

The first implementation must support at least:

* Weekly distance goal.
* Monthly distance goal.

The design should allow additional goal types to be added later without requiring the current user experience to be redesigned.

## 6.3 Goal definition

The user must be able to:

* Create a goal.
* Define its target value.
* Define the relevant period.
* View the goal's current progress.
* Modify an active goal.
* Remove/deactivate a goal.

For a weekly distance goal, for example:

> Target: 40 km per week.

## 6.4 Goal progress

The system must calculate progress from completed training.

A goal must display:

* Target.
* Current achieved value.
* Remaining amount.
* Percentage completion where meaningful.
* Period to which the goal applies.

The dashboard must surface active goals prominently enough that the user can understand current progress without opening a separate settings page.

---

# 7. Weekly Training Schedule

## 7.1 Objective

Allow the user to define a planned structure for the week before training takes place.

## 7.2 Schedule definition

The user must be able to define planned sessions for individual days of the week.

A planned session should support, at minimum:

* Day.
* Training type.
* Optional title/description.
* Optional target distance.
* Optional target duration.
* Optional target pace.
* Optional notes.

The system must not require every field to be populated.

## 7.3 Weekly schedule

The user must be able to create a recurring weekly template such as:

* Monday — Rest.
* Tuesday — Intervals — 8 km.
* Wednesday — Easy — 6 km.
* Thursday — Tempo — 10 km.
* Friday — Rest.
* Saturday — Long run — 18 km.
* Sunday — Easy — 6 km.

The weekly schedule should be usable as the basis for planning individual weeks.

## 7.4 Planned sessions

The system must distinguish between:

* A reusable weekly schedule/template.
* A specific planned session on a specific calendar date.
* A completed training imported or recorded for that date.

The user must be able to see whether planned training has been completed.

The system must not automatically mark a planned workout as completed solely because a training exists on the same day unless the relationship can be established reliably.

## 7.5 Planning and goals

Where a weekly schedule contains target distances, the system should make it possible to compare planned weekly distance against the active weekly distance goal.

The dashboard should therefore be able to show, where applicable:

* Weekly goal.
* Planned weekly distance.
* Completed weekly distance.
* Remaining planned training.

---

# 8. User Experience Requirements

The experience must remain simple and suitable for a single-user application.

The primary workflow should be:

**Dashboard → understand current state → Calendar → plan the week → Trainings → inspect/filter completed sessions.**

The dashboard should prioritize actionable information rather than presenting every available metric.

Charts must have:

* Clear labels.
* Understandable units.
* Meaningful time ranges.
* Tooltips or equivalent detail when exact values are useful.
* Empty states when insufficient data exists.

Analytics must degrade gracefully when some trainings lack GPS, pace, distance, or heart-rate data.

---

# 9. Data & Behavioral Requirements

The implementation must use the existing training data wherever possible.

The system must not require historical training data to be re-entered manually.

Calculated analytics must update when training data changes.

If a training is added, removed, or modified, relevant:

* Dashboard metrics.
* Trends.
* Personal bests.
* Goal progress.
* Calendar entries

must reflect the change.

The implementation should avoid introducing unnecessary complexity into the current data model. The current architecture is still considered work in progress.

---

# 10. Success Criteria

The iteration is successful when:

1. The dashboard provides a coherent view of current training state.
2. Weekly and monthly mileage trends are visible.
3. Pace and heart-rate trends are available when sufficient data exists.
4. Personal bests can be identified from recorded training data.
5. Trainings can be searched and filtered by tag, date range, and distance.
6. The calendar opens in a week/agenda view.
7. Planned and completed sessions are clearly distinguishable.
8. Users can navigate between calendar weeks.
9. Users can define and monitor weekly/monthly goals.
10. Users can define a weekly training schedule.
11. Planned sessions appear in the relevant calendar week.
12. Existing imported and recorded training functionality continues to work.
13. The application remains usable when there is insufficient historical data for analytics.

---

# 11. Validation Requirements

### Application integrity

* The application must build successfully after the changes.
* The application must run successfully in the expected development/runtime environment.
* Existing functionality must continue to work.
* No regressions in existing functionality are allowed.

### Test validation

* All existing tests must pass.
* If existing tests fail because of the changes, they must be fixed without changing the intended behavior of the application.
* New tests should be added where necessary to validate the new requirements, particularly:

  * Filtering combinations.
  * Analytics calculations.
  * Goal progress calculations.
  * Calendar/planned-session behavior.
  * Planned versus completed training state.

### Visual validation

The implementation must include visual evidence demonstrating the completed work.

The final deliverable must include screenshots or equivalent visual proof showing, at minimum:

* The new training dashboard.
* The weekly calendar/agenda.
* Training-list search/filtering.
* Goals and schedule configuration or their resulting dashboard/calendar state.

Where appropriate, before/after comparisons should be included for substantially modified existing screens.

---

# 12. Delivery Requirements

All changes must be delivered through a pull request.

The pull request must include:

* A concise summary of the implemented functionality.
* A description of behavioral and UX changes.
* Relevant test/validation results.
* Visual proof of the implemented changes.
* An explanation of any known limitations or assumptions.
* Confirmation that existing functionality was validated and no known regressions remain.

The implementation should remain intentionally lightweight. This iteration is intended to establish useful training analytics and planning workflows, not to finalize the application's long-term architecture.
