# FIT / TCX File Upload and Data Inspection — Initial Implementation

## 1. Objective

Implement the first end-to-end version of FIT and TCX activity file handling.

The application must allow a user to select FIT or TCX files from their computer, upload them to the server, process their contents, and inspect the activity data through a simple web interface.

The primary goal of this iteration is to prove that the complete flow works:

**File selection → Upload → Server-side parsing → Data extraction → Client-side display**

This is an initial functional implementation. Visual design and advanced data visualization are explicitly out of scope.

---

## 2. Scope

### In scope

The implementation must support:

- Selecting FIT files from the user's computer.
- Selecting TCX files from the user's computer.
- Uploading files to the backend.
- Server-side processing and parsing of FIT and TCX files.
- Extracting activity information from the files.
- Displaying uploaded files in a list or table.
- Selecting an individual file from the list.
- Displaying the data extracted from the selected file.
- Displaying GPS and activity-related information where available, including:
  - GPS coordinates
  - Heart rate
  - Distance
  - Speed
  - Timestamp
  - Other relevant activity fields available in the source file.

The existing application template must be used as the foundation. The existing React frontend and Go backend must be integrated rather than replaced.

### Out of scope

The following are not required for this iteration:

- Advanced maps or GPS route visualization.
- Charts or sophisticated data visualization.
- Advanced activity analytics.
- Garmin account integration.
- Automatic synchronization with Garmin services.
- User authentication or account management changes.
- Production deployment changes.
- Docker image or production-environment changes unless required to prevent breaking the existing application.
- Polished visual design.

---

## 3. User Flow

The expected user flow is:

1. The user opens the application.
2. The application displays a simple interface containing a file-selection/upload control.
3. The user selects one or more FIT or TCX files from their computer.
4. The application uploads the selected files to the server.
5. The server validates and processes each file.
6. Successfully processed files appear in a file list/table.
7. The user selects a file from the list.
8. The application displays information extracted from that file.
9. The user can select another file and inspect its data.

The interface should make the current state clear, including whether a file is uploading, has been processed successfully, or could not be processed.

---

## 4. Functional Requirements

### 4.1 File Selection

The frontend must provide a control that allows the user to select files from their computer.

The control must accept FIT and TCX files.

The application should prevent unsupported file types from being submitted where practical and must provide a clear error message when an unsupported file is selected.

The user must be able to select multiple files in a single operation.

### 4.2 File Upload

Selected files must be sent to the backend for processing.

The backend must receive the original file contents and process them server-side.

The frontend must provide sufficient feedback to indicate that the upload or processing is in progress.

### 4.3 FIT and TCX Processing

The backend must be capable of reading both supported formats:

- FIT
- TCX

The backend must extract structured activity data from the files rather than simply storing or displaying the raw file contents.

The processing must preserve the relationship between individual activity records and their associated timestamps and measurements.

When a supported file does not contain a particular data field, the application must not invent a value. The corresponding field should be omitted or displayed as unavailable.

### 4.4 File List

After successful processing, the frontend must display the uploaded files in a simple list or table.

Each entry must provide enough information to identify the file, at minimum its filename.

Where available, the interface may also display basic metadata such as:

- File type
- Activity date
- Duration
- Distance
- Number of recorded data points

The list must allow the user to select an individual file.

### 4.5 File Details

When the user selects a file, the frontend must display extracted information from that activity.

The displayed information must demonstrate that the file has been successfully parsed and contains structured activity data.

The detail view should include, where available:

- Filename
- Activity date/time
- Distance
- Duration
- Speed
- Heart rate
- GPS coordinates
- Number of recorded data points

The application should also display a representative set of GPS/activity records rather than requiring the user to inspect an entire potentially large dataset at once.

For example, a simple table containing timestamp, latitude, longitude, distance, speed, and heart rate is sufficient for this iteration.

### 4.6 Error Handling

The application must handle invalid or unsupported files gracefully.

At minimum, it must provide a clear user-facing error when:

- The file type is unsupported.
- The file cannot be parsed.
- The file is malformed.
- The server cannot process the upload.

An error processing one file must not cause successfully processed files to disappear or become inaccessible.

---

## 5. Backend Requirements

The Go backend must expose the functionality required for:

1. Receiving FIT and TCX files.
2. Processing the files.
3. Extracting structured activity information.
4. Returning the processed information to the frontend.
5. Providing sufficient error information when processing fails.

The backend must maintain a clear distinction between file-level metadata and individual activity records.

The extracted data model must be sufficiently generic to represent information common to both FIT and TCX files while allowing format-specific fields to be absent when they are not available.

The implementation should not assume that every FIT or TCX file contains the same fields.

---

## 6. Frontend Requirements

The React frontend must provide a minimal functional interface consisting of:

- A file-selection/upload control.
- An uploaded-file list or table.
- A selected-file detail area.

The interface does not need to be visually polished.

However, the following states must be visually understandable:

- No files uploaded.
- Files being processed.
- Files successfully processed.
- A file selected for inspection.
- Processing or upload failure.

Selecting an item in the file list must update the displayed details without requiring a full-page reload.

---

## 7. Data Display Requirements

The initial implementation does not require maps, charts, or advanced visualization.

A basic tabular representation of the extracted activity records is sufficient.

For example:

| Timestamp | Latitude | Longitude | Distance | Speed | Heart Rate |
| --------- | -------: | --------: | -------: | ----: | ---------: |
| ...       |      ... |       ... |      ... |   ... |        ... |

The exact set of displayed fields may vary depending on which fields are available in the source file.

The purpose of this view is to provide clear evidence that the application can successfully parse real FIT and TCX activity data.

---

## 8. Constraints

- The existing application template must remain the foundation of the implementation.
- The existing React frontend must be used.
- The existing Go backend must be used.
- Existing application functionality must not be unnecessarily modified or removed.
- The implementation only needs to be fully functional in the development environment for this iteration.
- Production deployment and Docker configuration do not need to be changed unless the implementation would otherwise break the existing project.
- The implementation should remain simple and focused on validating the end-to-end data flow.
- Implementation choices must not introduce unnecessary architectural complexity.

---

## 9. Success Criteria

The implementation is considered successful when all of the following are true:

1. A user can select a valid FIT file from their computer.
2. The file can be uploaded successfully.
3. The Go backend can parse the FIT file.
4. Extracted activity data is returned to the frontend.
5. The uploaded FIT file appears in the file list.
6. Selecting the FIT file displays its extracted data.

The same complete flow must work for a valid TCX file.

The displayed information must include real data extracted from the uploaded file, including GPS/activity records where those records exist in the source file.

Invalid or unsupported files must produce a clear error rather than causing the application to fail.

---

## 10. Validation Requirements

### Application Integrity

The application must build and run successfully in the existing development environment after the changes.

No regressions in existing functionality are allowed.

Existing frontend and backend behavior that is unrelated to this feature must remain functional.

### Test Validation

All existing tests must pass after implementation.

If any existing test fails because of the changes, the failure must be fixed without altering the intended behavior of the existing functionality.

New tests should be added where necessary to validate the new FIT/TCX processing and upload behavior.

At minimum, the implementation should validate:

- Successful FIT parsing.
- Successful TCX parsing.
- Handling of malformed files.
- Handling of unsupported file types.
- Correct representation of extracted activity records.

### Visual Proof of Work

The implementation must include visual evidence demonstrating the completed functionality.

The final deliverable must contain screenshots showing, at minimum:

1. The file-selection/upload interface.
2. A populated list containing uploaded FIT/TCX files.
3. A selected activity displaying extracted data.
4. GPS/activity records visible in the detail view.

If useful, before/after comparisons or a simple flow diagram may also be included.

---

## 11. Deliverables

The developer must deliver:

- The completed frontend implementation.
- The completed backend implementation.
- FIT file parsing and processing.
- TCX file parsing and processing.
- The file list/detail interface.
- Appropriate tests for the new behavior.
- Visual proof of the implemented functionality.
- A pull request containing all changes.

The pull request must include:

- A concise summary of the changes.
- Visual proof of the implemented functionality, including screenshots and/or diagrams.
- An explanation of the impact of the changes.
- Validation information confirming that the application builds and runs successfully.
- Test results confirming that the existing test suite passes.

---

## 12. Definition of Done

This task is complete when a developer or reviewer can start the application in the existing development environment, upload real FIT and TCX files, see those files listed, select an activity, and inspect actual GPS and activity data extracted by the backend.

The implementation should demonstrate a reliable end-to-end foundation for future iterations involving maps, charts, activity analysis, and richer GPS visualization.
