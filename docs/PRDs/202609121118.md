# Iteration 3 — Training Dashboard and Application UI

## 1. Objective

Transform the current application from a basic FIT-file upload and visualization tool into a simple running-training application.

The application must allow the user to:

* See an overview of their running activity from a dashboard.
* Upload new training tracks.
* Browse previously uploaded training tracks.
* Open an individual track and see its recorded FIT data.
* Add basic user-defined information to each training:

  * Name
  * Description
  * Tags
* Navigate between the main sections of the application through a consistent application layout.

This iteration is focused on the user interface, application structure, and the data/API required to support it.

The application does **not** need to implement training recommendations, AI analysis, race preparation logic, or advanced training planning in this iteration.

The data model and UI can remain intentionally simple and work-in-progress. Do not introduce abstractions or compatibility mechanisms specifically intended for future iterations.

---

# 2. Scope

This iteration includes:

### Client

* Application-wide layout.
* Left sidebar navigation.
* Dashboard page.
* Training/track list page.
* Training/track detail page.
* Upload track flow.
* Basic training metadata editing.
* Settings page placeholder.
* Improved visualization of FIT data.
* Reusable UI components and clear application structure.

### Server

* Extend the existing database model to store training metadata.
* Extend the existing API to expose training data.
* Provide dashboard statistics.
* Provide a list of uploaded trainings/tracks.
* Provide individual training details.
* Support updating training metadata.
* Continue supporting FIT-file upload and storage.

### Out of scope

The following must not be implemented as part of this iteration:

* AI-generated training recommendations.
* Half-marathon training plans.
* Automatic workout classification.
* Training load calculations.
* Advanced athlete analytics.
* User accounts/authentication unless already required by the existing application.
* Social features.
* Sharing workouts.
* Complex tagging systems.
* Advanced data modelling intended to support future product requirements.

---

# 3. Application Structure

The application should have a consistent application shell around the main pages.

The primary navigation must be a left sidebar.

The sidebar must contain:

1. An application/product identity at the top.
2. A prominent **Add Track / Upload Track** action.
3. Navigation options:

   * Dashboard
   * Tracks / Trainings
   * Settings

The sidebar should remain visually consistent when navigating between pages.

The main content area should be used by the active page.

The application should also include a footer where appropriate, containing only useful application-level information. The footer should not consume significant screen space.

The overall interface should feel like a simple training application rather than a file-management interface.

---

# 4. Dashboard

The dashboard must become the application's default/index page.

The dashboard should provide a quick overview of the user's running activity.

At minimum, it should display aggregated metrics based on the uploaded training data:

* Total distance.
* Elevation gain.
* Number of training sessions.
* Heart-rate information where available.
* Running activity over time.

The dashboard should provide different time perspectives, such as:

* Today.
* Current week.
* Current month.
* Overall/all recorded activity.

The exact presentation can be chosen based on what produces the clearest UI.

For example, the dashboard may contain:

* Summary metric cards.
* Distance over time chart.
* Elevation information.
* Heart-rate information.
* Recent training list.
* Recent activity visualization.

The dashboard must use real data retrieved from the server rather than hardcoded example values.

If a particular metric cannot be calculated because the required FIT data is unavailable, the UI must handle this gracefully rather than displaying misleading values.

---

# 5. Training / Track List

Create a dedicated page showing the user's uploaded trainings/tracks.

Each training should be represented as a concise list or card containing useful information such as:

* Training name.
* Date.
* Distance.
* Duration.
* Elevation gain.
* Average heart rate when available.
* Relevant tags.

The list must be populated from the server.

The user must be able to select a training and navigate to its detail page.

The list should clearly distinguish between:

* The user's own metadata.
* Data extracted from the FIT file.

For example, the training name and tags are user-defined metadata, while distance, heart rate and elevation are derived from the uploaded file.

---

# 6. Training Detail

Each uploaded FIT file must have a corresponding training/track detail view.

The detail page should combine user-defined information with the data extracted from the FIT file.

The page must provide:

### User-defined information

The user must be able to view and edit:

* Name.
* Description.
* Tags.

The UI should make it clear that these fields are editable.

### FIT-derived information

Continue displaying the FIT information that is currently available in the application.

The exact set of FIT-derived parameters should follow the existing implementation rather than being unnecessarily redesigned in this iteration.

Where applicable, show information such as:

* Distance.
* Duration.
* Speed/pace.
* Heart rate.
* Elevation.
* GPS data.
* Other useful FIT metrics already supported by the application.

---

# 7. Track Visualization

Improve the current FIT-data visualization so that it feels like part of a training application.

The track detail page should include a visual representation of the recorded activity.

At minimum, the track visualization should show:

* The path of the activity.
* A clear indication of the relative position of the recorded points.
* A common origin/reference system for the coordinates.

For this iteration, the visualization does not need to be geographically accurate or use real map tiles.

Relative coordinates derived from the recorded GPS points are sufficient.

The visualization should prioritize:

* Clear representation of the shape of the run.
* Correct relative positioning of points.
* Readability.
* Appropriate sizing within the page.

If time-series data is already available from the FIT file, the detail page should also provide charts for relevant metrics, particularly:

* Heart rate over time/distance.
* Pace or speed over time/distance.
* Elevation over time/distance.

The charts should use the actual FIT data.

The visualization should not require advanced mapping functionality in this iteration.

---

# 8. Upload Track Flow

The existing FIT upload functionality must remain available.

The primary way to start a new training should be the **Upload Track / Add Track** action in the sidebar.

The upload flow must:

1. Allow the user to select a FIT file.
2. Upload the file using the existing backend functionality.
3. Store the FIT file using the existing storage mechanism.
4. Store the corresponding training data in the database.
5. Create a training/track record.
6. Navigate the user to the newly created training or its detail page.

After upload, the user must be able to add:

* Name.
* Description.
* Tags.

The upload operation must not require the user to manually enter FIT-derived metrics.

Those metrics must continue to come from the uploaded file.

---

# 9. Data Model

Extend the existing training/track database representation with simple user-defined metadata.

At minimum, each training must support:

* `name`
* `description`
* `tags`

The existing FIT-file information and storage references must continue to work.

The database must retain the relationship between:

* The uploaded FIT file.
* The corresponding training/track.
* The FIT-derived training data.
* The user's metadata.

Do not design a generalized or highly normalized metadata system at this stage.

A simple implementation appropriate for the current WIP application is preferred.

The exact schema structure should follow the existing project conventions.

---

# 10. API Requirements

Extend the server API so the client can retrieve and modify the information required by the new UI.

The API must support:

### Dashboard data

Provide the aggregated data required to render the dashboard, including, where available:

* Distance.
* Elevation gain.
* Number of trainings.
* Heart-rate metrics.
* Time-series/activity summaries required by the dashboard.

### Training list

Provide the data required to display the training/track list.

### Training detail

Provide:

* Training metadata.
* FIT-derived metrics.
* Available time-series data.
* Track/GPS data required for visualization.
* File/storage reference where required by the existing application.

### Training metadata update

Allow the client to update:

* Name.
* Description.
* Tags.

### Upload

Preserve the existing FIT upload functionality and integrate it with the new training model.

API responses should contain enough information for the client to render the relevant pages without duplicating server-side calculations unnecessarily.

---

# 11. Client Architecture

The client should be reorganized into a clear application structure suitable for a multi-page application.

Use reusable components for common UI elements such as:

* Application shell.
* Sidebar.
* Navigation items.
* Metric cards.
* Training cards/list items.
* Charts.
* Track visualization.
* Metadata editing controls.

Pages/routes should be separated clearly into:

* Dashboard.
* Tracks/Trainings.
* Training detail.
* Settings.

Avoid putting the entire application UI into a single large component.

The implementation should follow the existing project's conventions and use clear separation between page-level components and reusable UI components.

---

# 12. Settings

Add a Settings section to the application navigation.

For this iteration, Settings does not need significant functionality.

It should provide a valid page and establish the location for future application configuration.

Do not invent unnecessary settings simply to populate the page.

---

# 13. UX Requirements

The application must provide a coherent navigation experience.

The user should always be able to:

* Return to the dashboard.
* Open the training list.
* Upload a new training.
* Open an existing training.
* Edit its basic metadata.
* Return to the training list.

Loading, empty, and error states must be handled explicitly.

Examples:

* No trainings uploaded yet → show an appropriate empty state and a clear upload action.
* Dashboard with no activity → show zero/empty metrics without appearing broken.
* Missing heart-rate data → do not display fabricated values.
* Upload failure → clearly communicate that the upload failed.
* Training not found → show an appropriate error state.

The UI should work at common desktop viewport sizes and remain usable on smaller screens.

---

# 14. Visual Design

The interface should move away from the current basic upload/file-viewer appearance and establish a consistent application visual language.

The design should emphasize:

* Clear hierarchy.
* Readable metrics.
* Consistent spacing.
* Consistent typography.
* Clear navigation.
* Distinct primary actions.
* Easy scanning of training information.
* Appropriate use of charts and visualizations.

The dashboard should visually communicate that this is a running-training application.

Avoid excessive decoration. The interface should remain simple and information-focused.

---

# 15. Success Criteria

This iteration is complete when:

1. Opening the application displays the Dashboard as the main page.
2. The user can navigate through the sidebar to:

   * Dashboard.
   * Tracks/Trainings.
   * Settings.
3. The user can upload a FIT file from the sidebar.
4. A successful upload creates a training/track record.
5. The uploaded FIT file continues to be stored using the existing storage mechanism.
6. The training appears in the training list.
7. The user can open the training detail page.
8. The detail page displays the existing FIT-derived information.
9. The user can add and edit:

   * Name.
   * Description.
   * Tags.
10. The dashboard displays real aggregated training data.
11. The dashboard includes useful visual metrics/charts.
12. The training detail page provides an improved visualization of the recorded track.
13. Relevant FIT time-series data is visualized through charts where available.
14. Existing upload and FIT-processing functionality continues to work.
15. Empty, loading, and error states are handled.
16. The application has a consistent layout and reusable component structure.

---

# 16. Validation Requirements

## Application Integrity

The application must build and run successfully after all changes.

No existing functionality may regress as a result of this iteration.

Existing FIT upload, storage, parsing, and visualization behavior must continue to work unless explicitly replaced by the requirements above.

## Test Validation

All existing tests must pass.

If existing tests fail because of changes introduced in this iteration, they must be fixed without changing the intended behavior of the application.

Add new tests only where necessary to validate the new behavior, particularly:

* Training metadata.
* Dashboard aggregation.
* Training list/detail behavior.
* Metadata updates.
* Upload-to-training creation flow.

## Visual Proof

The implementation must include visual evidence demonstrating the completed work.

At minimum, provide screenshots showing:

1. Dashboard.
2. Sidebar/navigation.
3. Training list.
4. Training detail page.
5. FIT track visualization and charts.
6. Upload flow or newly created training.

If appropriate, include before/after comparisons showing the improvement over the previous interface.

The visual proof must be included in the final deliverable.

---

# 17. Pull Request Requirements

All changes must be delivered through a pull request.

The pull request must include:

* A concise summary of the changes.
* A description of the new application flow.
* A summary of client-side changes.
* A summary of server/database/API changes.
* Test/validation results.
* Visual proof of the implemented UI, including screenshots and/or relevant diagrams.
* A short explanation of the impact of the changes on the existing application.

The pull request must clearly indicate whether all tests pass and whether the application builds and runs successfully.

---

# 18. Implementation Principle

Keep this iteration intentionally simple.

The goal is to establish a usable running-training application around the existing FIT upload functionality, not to design the final architecture for future AI coaching or advanced analytics.

Prefer straightforward solutions that fit the current application and existing codebase.

Do not introduce complexity solely because a future version might need it.
