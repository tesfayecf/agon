# PRD — Iteration 4: Professional UI & Calendar-Centred Training Log

## 1. Objective

Transform the current application into a more professional and serious running training log, with the calendar becoming a more prominent part of the core user experience.

The application should feel intentionally designed and engineered, with a coherent visual system and clear information hierarchy. It should not feel like a prototype or an AI-generated interface.

This iteration has two primary goals:

1. Improve the overall interface and visual quality of the application.
2. Introduce and integrate a calendar as a central way to navigate and review training activity.

The backend should remain intentionally simple. It should primarily support uploading, storing, retrieving, and displaying training files and their associated data.

No AI coaching or training recommendation functionality is part of this iteration.

---

## 2. Scope

### In scope

* Professional redesign of the existing application interface.
* Improved application layout and navigation.
* Calendar as a prominent part of the application.
* Display of existing training activity in the calendar.
* Navigation between dates/months.
* Ability to select a training from the calendar and access its details.
* Integration between calendar, training list, and training detail views.
* Minor backend/API changes only where required by the calendar or improved UI.
* Continued FIT training upload and storage.
* Appropriate processing of FIT data using the simplest suitable approach.

### Out of scope

* AI-generated training recommendations.
* Half-marathon training plans.
* Automatic workout planning.
* Advanced training-load calculations.
* Multi-user functionality.
* Social functionality.
* Complex backend analytics.
* Major database restructuring.
* Future-proof abstractions that are not required by the current functionality.

---

# 3. Product Direction

The application should evolve from a file-upload interface into a personal training log.

The primary mental model should be:

**Calendar → Training → Training details**

The calendar should make it immediately obvious which days contain training activity and allow the user to quickly access those sessions.

The interface should remain simple because the application is currently intended for a single user with a relatively small amount of training data.

---

# 4. Professional UI Redesign

The entire existing interface should be reviewed and improved rather than redesigning only individual pages.

The visual result must feel like a deliberately designed professional application.

The design should have:

* Clear visual hierarchy.
* Consistent spacing.
* Consistent typography.
* Consistent component styling.
* Clear primary and secondary actions.
* Appropriate use of whitespace.
* Strong alignment and layout consistency.
* Professional presentation of metrics and data.
* Clear navigation.
* Consistent states for loading, empty data, errors, and success.
* A restrained and coherent visual language.

Avoid visual patterns that make the application appear automatically generated or assembled from unrelated UI components.

Do not add decorative elements that do not improve usability.

The design should prioritize information and usability over visual effects.

---

# 5. Application Navigation

Maintain a clear application-wide navigation structure.

The left sidebar should remain the primary navigation mechanism.

It should provide access to:

* Dashboard.
* Calendar.
* Trainings / Tracks.
* Settings.

The upload/add-training action should remain clearly accessible from the sidebar.

The Calendar should receive increased visual prominence compared with the previous iteration because it is now one of the primary ways of interacting with the training log.

The active navigation state must always be visually clear.

---

# 6. Calendar

## 6.1 Purpose

The calendar should become a central part of the application and provide a chronological view of the user's training history.

It must use real training data already stored by the application.

The calendar should make it easy to answer:

* Did I train on this day?
* What training did I do?
* How much did I run?
* What type of activity was recorded?
* How can I open the full training?

---

## 6.2 Calendar View

Implement a calendar interface that displays training activity by date.

The calendar should provide:

* Clear day/date representation.
* Visual indication of days containing training.
* Training information directly within or adjacent to the relevant date.
* Navigation between calendar periods.
* A clear indication of the currently selected date or period.

A monthly calendar view is the default expected view unless the existing application structure makes another view significantly more appropriate.

The user must be able to navigate backwards and forwards through available periods.

---

## 6.3 Training Representation

Days containing training should be visually distinguishable from days without training.

Where appropriate, the calendar should display concise information such as:

* Distance.
* Training name.
* Duration.
* Other useful summary information already available from the FIT file.

The calendar must remain readable when multiple training sessions exist.

Do not attempt to display every FIT metric directly inside calendar cells.

---

## 6.4 Calendar Interaction

The user must be able to select a training from the calendar.

Selecting a training should provide access to its existing detail view.

The interaction should make the relationship between the calendar entry and the underlying training explicit.

For example:

**Calendar day → Training summary → Training detail**

The user should not need to search manually through the training list to open a training visible on the calendar.

---

# 7. Calendar and Dashboard Integration

The dashboard should be updated so that the calendar does not feel like an isolated feature.

The dashboard should provide a clear entry point into the user's training history.

Where appropriate, the dashboard may include:

* Recent training activity.
* A compact calendar/activity preview.
* Current-period distance.
* Number of sessions.
* Other existing training metrics.

The calendar itself should remain the more detailed chronological view.

Do not duplicate unnecessary functionality between Dashboard and Calendar.

---

# 8. Training List Integration

The existing training list should remain available.

The list and calendar must represent the same underlying training records.

A training opened from:

* Calendar
* Dashboard
* Training list

must lead to the same training detail experience.

The user should not encounter different representations or duplicated records depending on how they access the training.

---

# 9. Training Detail

The existing training detail functionality should remain available and should be visually integrated with the new design.

A training detail page should continue to display:

### User-defined information

* Name.
* Description.
* Tags.

### FIT-derived information

Where currently available:

* Distance.
* Duration.
* Pace/speed.
* Heart rate.
* Elevation.
* GPS/track information.
* Other supported FIT metrics.

The existing track and time-series visualizations should remain functional.

The redesign should focus on presentation and usability rather than introducing additional analytics.

---

# 10. Training Upload

Uploading a training remains a core backend-supported operation.

The user must be able to:

1. Select a training FIT file.
2. Upload it.
3. Store the file.
4. Create or update the corresponding training record.
5. See the new training in the application.
6. See the training on the appropriate calendar date.
7. Open the training detail page.

The upload experience should be visually consistent with the redesigned application.

The user-defined metadata should remain available:

* Name.
* Description.
* Tags.

---

# 11. Backend and Data Processing

The backend should remain deliberately simple.

The primary backend responsibilities should be:

* Receive uploaded training files.
* Store the files.
* Store the associated training record.
* Retrieve training records.
* Retrieve the information required by the client.
* Support updating basic training metadata where necessary.

Do not introduce unnecessary backend processing.

## FIT Data Processing

Determine where FIT-file parsing and metric processing should occur based on the current implementation and the simplest appropriate architecture.

If FIT data can be processed reliably on the client without creating unnecessary complexity, it is acceptable to keep that processing on the client.

If existing server-side processing already performs this functionality effectively, do not move it merely for architectural reasons.

The requirement is to choose the simplest approach that works reliably for the current single-user application.

The server should not become an analytics engine in this iteration.

---

# 12. Database

Avoid unnecessary database changes.

The existing database structure should be reused wherever possible.

Only modify the schema if the calendar or required training metadata cannot be implemented correctly using the existing model.

The database must retain enough information to associate each training with its date and uploaded file so that the calendar can display it correctly.

Do not introduce:

* Multi-user abstractions.
* Complex analytics tables.
* Training-plan tables.
* AI-related data structures.
* Generalized event systems.

The data model should remain simple and appropriate for the current WIP stage.

---

# 13. API

Only extend the API where required by the new UI.

The API must provide the client with the information necessary to:

* Retrieve training records.
* Determine training dates.
* Display calendar activity.
* Open training details.
* Upload training files.
* Update training metadata where supported.

If the existing API already provides the required information, reuse it rather than introducing duplicate endpoints.

Calendar-specific server functionality should only be added if the existing API cannot efficiently provide the required data.

---

# 14. Frontend Architecture

The frontend should be structured as a maintainable application rather than a collection of page-specific implementations.

Use clear separation between:

* Application layout.
* Navigation.
* Pages.
* Calendar components.
* Training components.
* Data visualization components.
* Reusable UI components.

The calendar should be implemented as a reusable feature rather than tightly coupling calendar logic to a single page.

Avoid unnecessary abstraction. Components should be created where they represent meaningful reusable UI or application functionality.

---

# 15. UX States

The application must explicitly handle:

### Empty calendar

When no training exists, the calendar should clearly communicate that there is no recorded activity and provide an obvious way to upload a training.

### Empty date

A day without training should remain visually clear and should not appear broken.

### Loading

Calendar and training data should provide an appropriate loading state.

### Errors

If training data cannot be retrieved, the application must communicate the problem clearly.

### Missing metrics

If a FIT file does not contain a particular metric, the UI must not fabricate a value.

---

# 16. Responsive Behaviour

The redesigned interface and calendar must remain usable across common desktop screen sizes.

The calendar must adapt appropriately to smaller available widths.

Information should be reduced or reorganized when necessary rather than creating unreadable calendar cells or horizontal overflow.

The sidebar and primary navigation must remain usable on smaller screens according to the application's existing responsive conventions.

---

# 17. Success Criteria

The iteration is complete when:

1. The application has a noticeably more professional and cohesive visual design.
2. The application no longer feels primarily like a file-upload/prototype interface.
3. Calendar is a first-class navigation option.
4. Calendar activity is populated from real training data.
5. Training days are clearly identifiable.
6. The user can navigate between calendar periods.
7. The user can select a training from the calendar.
8. Selecting a calendar training opens its corresponding training detail.
9. Calendar, dashboard, and training list all reference the same underlying training records.
10. Existing FIT upload functionality continues to work.
11. Uploaded trainings appear on the correct calendar date.
12. Existing training detail and FIT visualizations continue to work.
13. The backend remains simple and has only been modified where necessary.
14. No unnecessary database restructuring has been introduced.
15. The application handles empty, loading, and error states correctly.
16. The application builds and runs successfully.
17. Existing functionality does not regress.

---

# 18. Validation Requirements

## Application Integrity

The application must build and run successfully after the changes.

No regressions in existing functionality are allowed.

Existing FIT upload, storage, parsing, training display, and visualization functionality must continue to work.

## Test Validation

All existing tests must pass.

If tests fail because of changes introduced in this iteration, they must be fixed without altering the intended behaviour.

Add new tests only where necessary to validate:

* Calendar rendering.
* Training-to-date association.
* Calendar navigation.
* Opening a training from the calendar.
* Upload-to-calendar integration.
* Any changed training metadata behaviour.

## Visual Proof

The implementation must include visual evidence of the completed work.

The final deliverable must include screenshots demonstrating at least:

1. The redesigned application shell/sidebar.
2. The redesigned Dashboard.
3. The new Calendar view.
4. A calendar containing real training activity.
5. A training opened from the calendar.
6. The improved training detail interface.

The screenshots should demonstrate the visual improvement and the relationship between the calendar and training records.

## Pull Request

All changes must be delivered through a pull request.

The pull request must include:

* Summary of changes.
* Description of the new calendar functionality.
* Summary of UI/UX improvements.
* Summary of any backend/API/database changes.
* Test results.
* Confirmation that the application builds and runs successfully.
* Visual proof of the changes.
* Explanation of the impact on existing functionality.

---

# 19. Guiding Principle

Keep the implementation focused.

This iteration is primarily a **UI/UX improvement plus calendar functionality**.

The backend should remain a lightweight layer for storing and retrieving training files and their associated records. Do not introduce backend complexity merely to anticipate future AI coaching, advanced analytics, or multi-user functionality.

The desired product direction is:

**Upload training → store training → see it on the calendar → open the training → review its data.**

Future iterations can build more advanced analytics and AI-based training recommendations on top of this foundation.
