# Product Requirement Document: File Storage Integration & Fix File Visualization

## 1. Objective

Integrate SQL database and Garage S3 object storage to enable simple file uploading, persistence, and UI rendering. Additionally, enhance the UI visualization for fix files by adding time series charts and a 2D canvas track view using relative coordinates.

---

## 2. Scope

### In Scope

* Database schema to track uploaded fix files and their S3 metadata.
* Upload mechanism connecting the application to Garage S3 storage and saving metadata to the SQL database.
* Simple file listing and retrieval in the UI from the database and Garage S3.
* Enhanced UI rendering for fix file content:
* Time series charts for numerical data.
* 2D Canvas element rendering the track layout based on relative coordinates measured from a local origin (0,0).



### Out of Scope

* Forward-compatible or extensible database schemas and file organization models (WIP prototype design).
* Real-world map tile integration, GPS map overlays, or external geospatial APIs.
* User authentication, permission models, or multi-tenant access controls for files.

---

## 3. Functional Requirements

### 3.1 File Storage & Database Integration

* **Upload Handler:** The system shall accept file uploads via the UI and store the raw file bytes in Garage S3 storage.
* **Database Persistence:** Upon successful upload to S3, the system shall insert a record into the SQL database containing essential file metadata (e.g., file identifier, file name, S3 object key, upload timestamp).
* **File Retrieval & List:**
* The system shall query the SQL database to list available uploaded files in the UI.
* The system shall allow users to select a file from the list to fetch its contents directly from Garage S3 for rendering.



### 3.2 Enhanced Fix File UI Visualization

* **Time Series Charts:**
* The system shall parse time series data from the selected fix file.
* The system shall display line charts plotting recorded variables over time (e.g., speed vs. time, altitude vs. time, or available telemetry metrics).


* **Track Canvas View:**
* The system shall parse coordinate data from the fix file.
* The system shall plot the path using a standard HTML canvas element.
* The system shall map coordinates relative to an arbitrary common origin point (0,0).
* The canvas track must auto-scale and center the path within the canvas viewport.



---

## 4. Behavioral Expectations

* **File Selection:** Selecting a file record from the database list must trigger a fetch request to retrieve the corresponding file from Garage S3 and automatically update the chart and canvas visualizations.
* **Visualization Loading:** If a fix file contains invalid or unparseable data, the system shall render a user-friendly error message within the visualization pane without crashing the page.

---

## 5. Execution & Validation Requirements

### 5.1 Application Integrity

* The application must build and run successfully after changes.
* No regressions in existing functionality are allowed.

### 5.2 Test Validation

* All existing tests must pass.
* If tests fail, they must be fixed without altering intended behavior.
* New tests should be added only if necessary to validate new behavior.

### 5.3 Visual Proof of Work

The implementation must include visual evidence of changes in the final deliverable:

* Screenshots of the file upload and list interface showing database-backed files.
* UI screenshots showing rendered time series charts.
* UI screenshots of the relative-coordinate 2D track canvas view.

### 5.4 Pull Request Requirement

All changes must be delivered via a pull request containing:

* Summary of changes.
* Visual proof (screenshots or recorded clips).
* Explanation of impact (what improved, what changed).
